# 游戏网关服务设计文档

## 一、项目概述

### 1.1 项目定位

游戏网关（Game Gateway）是游戏架构中的核心组件，负责客户端与游戏服务之间的消息转发和协议转换。本项目实现了一个高性能、可扩展的游戏网关服务。

### 1.2 架构图

```
┌─────────────┐     WebSocket/TCP      ┌─────────────┐
│             │ ◄─────────────────────► │             │
│   客户端    │                        │  游戏网关   │
│ (Player)   │                        │   (Gate)   │
│             │                        │             │

                                       ┌─────────────┐

                                       │  (Game)    │
                                       └─────────────┘
```

## 二、核心设计决策

### 2.1 为什么选择二进制协议？

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| JSON | 人类可读、易调试 | 体积大、解析慢 | Web API |
| Protobuf | 体积小、性能高 | 需要IDL定义 | 强类型服务通信 |
| 自定义二进制 | 完全可控、高性能 | 维护成本高 | 游戏/实时通信 |

**决策：自定义二进制协议**

理由：
1. 游戏对性能要求极高，需要最小化网络开销
2. 消息类型固定，便于优化
3. 可以精确控制每个字节

### 2.2 为什么使用Netty？

**Netty优势：**
- 零拷贝：直接操作堆外内存
- 异步非阻塞：支持高并发连接
- 丰富的协议支持：TCP/UDP/WebSocket
- 成熟稳定：大量生产环境验证

### 2.3 为什么选择Redis Stream做消息队列？

**对比其他方案：**

| 方案 | 优点 | 缺点 |
|------|------|------|
| Redis Pub/Sub | 简单、低延迟 | 不持久化 |
| Kafka | 高吞吐、持久化 | 部署重 |
| RabbitMQ | 功能丰富 | 性能一般 |
| Redis Stream | 持久化、消费者组、简单 | 相对Kafka吞吐较低 |

**决策：Redis Stream**

理由：
1. 游戏消息量级适中，Redis足够
2. 消费者组支持多Gate实例负载均衡
3. 消息持久化保证离线消息不丢失
4. 部署简单，与网关共用Redis

### 2.4 离线消息策略

**问题：** 玩家离线时，消息如何处理？

**方案对比：**

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| 丢弃 | 离线消息直接丢弃 | 简单 | 体验差 |
| 存储 | 存储到数据库/Redis | 消息不丢失 | 实现复杂 |
| 混合 | 少量存储，大量通知重登 | 平衡 | 需要客户端配合 |

**决策：混合策略**

- 离线消息 ≤ 200条：逐条存储到Redis Stream
- 离线消息 > 200条：发送relogin通知，让客户端重新登录
- 玩家上线时拉取离线消息

## 三、模块设计

### 3.1 消息协议模块

#### 3.1.1 消息格式

```
┌────────────────────────────────────────────────────────────┐
│                      消息结构（14+N字节）                    │
├────────────┬────────────┬────────────┬────────────┬─────────┤
│   flags    │  sequence  │ messageId │bodyLength │ requestId│
│   (2字节)  │  (2字节)   │  (2字节)  │  (4字节)  │ (4字节) │
├────────────┴────────────┴────────────┴────────────┴─────────┤
│                         body (N字节)                       │
│                    JSON格式的二进制数据                      │
└────────────────────────────────────────────────────────────┘
```

#### 3.1.2 消息ID生成

使用FNV哈希算法从消息名称生成ID：

```
消息名称格式: {模块}.{操作}
例如: auth.login, battle.move, chat.send

ID生成: FNV-64(hash) & 0xFFFF
```

**为什么这样做？**
- 自动生成ID，无需手动维护
- 相同名称总是生成相同ID
- 16位ID足够使用（65535个消息类型）

### 3.2 连接管理模块

#### 3.2.1 状态机

```
┌─────────────┐     认证成功      ┌─────────────┐
│ CONNECTING  │ ───────────────► │AUTHENTICATED│
│  (连接未认证)│                  │  (已认证)   │
└─────────────┘                  └──────┬──────┘
       ▲                                 │
       │         超时/断开               │
       └─────────────────────────────────┘
              (进入DISCONNECTED)
```

#### 3.2.2 心跳机制

- 客户端：每30秒发送一次心跳
- 服务器：每30秒检查一次，超时300秒则断开
- 使用ScheduledExecutorService实现定时任务

### 3.3 消息路由模块

#### 3.3.1 设计模式：责任链 + 策略

```
Client → Handler1 → Handler2 → Handler3 → Business Handler
         (认证)    (日志)    (限流)    (分发)
```

每个Handler职责单一，便于扩展和测试。

### 3.4 安全模块

#### 4.4.1 Token认证流程

```
1. 客户端登录 → Gate
2. Gate → Game (验证用户名密码)
3. Game → Gate (返回Token)
4. Gate → 客户端 (返回Token)
5. 后续请求携带Token
```

#### 4.4.2 限流算法：滑动窗口

```
时间轴: ──────────────────────────────────────────►
        │←── windowMs ─→│
        │   [请求1]       │
        │     [请求2]     │
        │       [请求3]   │
        │         [请求4] │ ← 当前请求，如果超出限制则拒绝
        
优势：比计数器更平滑，避免突发流量
```

#### 4.4.3 熔断器模式

```
状态转换:
CLOSED(正常) ──失败次数超过阈值──► OPEN(熔断)
  ▲                                      │
  │                                      │
  └──── 连续成功2次 ◄────── 超时 ─────────┘
  (HALF_OPEN，半开)
  
作用：防止故障服务被继续调用，保护系统
```

### 3.5 离线消息模块

#### 3.5.1 Redis Stream使用


## 四、性能优化

### 4.1 网络层优化

1. **Netty ByteBuf**：零拷贝，直接操作堆外内存
2. **TCP_NODELAY**：禁用Nagle算法，降低延迟
3. **SO_KEEPALIVE**：检测连接存活

### 4.2 压缩策略

- 仅对 > 64字节的消息压缩
- 使用DEFLATE算法（比gzip更轻量）
- 压缩后体积未减小则放弃压缩

### 4.3 多线程模型

```
Boss Group: 1个线程  ←  接受连接
Worker Group: CPU*2  ←  处理IO事件

业务处理: 线程池(4个线程)
  - 消息编解码
  - 业务逻辑处理
  - RPC调用
```

- JsonMessageBody：JSON格式
- ProtobufMessageBody：Protobuf格式（可扩展）

### 5.3 集群部署

```
                    ┌─────────────┐
                    │   负载均衡   │
                    │  (Nginx/LVS) │
                    └──────┬──────┘
                           │
         ┌─────────────────┼─────────────────┐
         │                 │                 │
         ▼                 ▼                 ▼
    ┌─────────┐      ┌─────────┐      ┌─────────┐
    │ Gate-01 │      │ Gate-02 │      │ Gate-03 │
    └────┬────┘      └────┬────┘      └────┬────┘
         │                 │                 │
         └─────────────────┼─────────────────┘
                           │
                           ▼
                    ┌─────────────┐

                    └─────────────┘
```

每个Gate实例：
- 无状态部署
- 通过Redis共享状态
- 支持水平扩展
