# 生产级框架差距分析与开发计划清单

> 分析日期：2026-03-16
> 分析范围：gate-service、game-service、login-service、center-service、player-client
> 优先级定义：P0 = 生产上线必须 | P1 = 上线后短期补齐 | P2 = 长期优化

**已实现核心能力**：WebSocket 网关（Netty）、gRPC 双向 Stream + 统一连接池、Redis 服务发现、离线消息（Redis Stream）、二进制协议编解码、消息路由/分发、登录路由、配置下发、Game 状态管理。

## 一、基础设施与 DevOps

### 1.1 CI/CD 流水线

- **当前状态**：无任何 CI/CD 配置（无 `.github/workflows`、Jenkinsfile 等）
- **差距**：代码提交无自动构建、测试、镜像推送；无法保证主分支可发布
- **建议方案**：创建 GitHub Actions workflow：`mvn clean verify` → JaCoCo 覆盖率检查 → `docker build & push`；分 PR 检查和 main 分支部署两个 workflow
- **优先级**：P0
- **涉及模块**：全部

### 1.2 Docker 健康检查修复

- **当前状态**：`docker-compose.yml` 中 game-1001 使用 `curl http://localhost:8081/api/game/health`，但 game-service 实际只暴露 gRPC 端口，无 HTTP 端口
- **差距**：容器健康检查始终失败或依赖不生效，Gate 启动依赖 `service_healthy` 可能卡死
- **建议方案**：方案一：game-service 实现 gRPC Health Checking Protocol，使用 `grpc_health_probe` 做健康检查；方案二：game-service 通过 Netty 暴露独立的轻量 HTTP 健康检查端口；推荐方案一
- **优先级**：P0
- **涉及模块**：game-service、docker-compose.yml

### 1.3 docker-compose 环境变量对齐

- **当前状态**：Gate 容器使用 `GAME_HOST=game-1001`、`GAME_PORT=8081`（HTTP），但代码已切换到 gRPC 通信（`gate.games` 配置 gRPC 端口）
- **差距**：环境变量与实际架构不一致，容器化部署时 Gate 无法正确连接 Game
- **建议方案**：更新 docker-compose.yml，Gate 使用 `GAME_1001_HOST`/`GAME_1001_PORT`（gRPC 9090），Game 暴露 gRPC 端口；添加 Redis 密码环境变量；补充 login-service 和 center-service 容器
- **优先级**：P0
- **涉及模块**：docker-compose.yml、gate-service、game-service

### 1.4 多环境配置 Profiles

- **当前状态**：仅一份配置文件，通过环境变量覆盖
- **差距**：开发环境与生产环境使用相同配置结构，无法区分日志级别、Redis 集群模式、TLS 开关等
- **建议方案**：为每个服务创建 `config-dev.yml`、`config-prod.yml`；通过启动参数或 `APP_ENV` 环境变量切换；dev 使用 DEBUG 日志 + 单节点 Redis + 明文；prod 使用 INFO 日志 + Redis Sentinel + TLS
- **优先级**：P1
- **涉及模块**：全部

### 1.5 K8s 部署清单

- **当前状态**：无 Kubernetes manifests
- **差距**：无法在 K8s 集群上部署和弹性伸缩
- **建议方案**：创建 Deployment、Service、ConfigMap、HPA 清单；配合 Helm Chart 管理多环境
- **优先级**：P2
- **涉及模块**：全部

### 1.6 README 与实际架构对齐

- **当前状态**：根目录 `README.md` 描述为"无 Redis 版本，Gate 与 Game 通过 HTTP 直连"，与实际主分支（gRPC + Redis）不一致
- **差距**：新人或运维人员阅读 README 会产生误解
- **建议方案**：重写 README，反映当前架构（gRPC + Redis + 5 服务）；将旧 HTTP 描述移入历史分支说明
- **优先级**：P0
- **涉及模块**：README.md

## 二、可观测性（Observability）

### 2.1 健康检查端点

- **当前状态**：所有服务均无标准健康检查端点
- **差距**：无标准健康检查接口，容器编排和负载均衡无法判断实例是否就绪
- **建议方案**：gate-service 通过 Netty 在独立端口暴露 `/health`、`/ready` 端点；game-service 实现 gRPC Health Checking Protocol；login/center 在现有 HTTP 框架中添加 `/health` 端点
- **优先级**：P0
- **涉及模块**：全部

### 2.2 Micrometer + Prometheus 集成

- **当前状态**：gate-service 有手写 `MetricsCollector`（内存 AtomicLong 计数 + 60s 日志输出），未暴露 HTTP 端点，未使用 Micrometer
- **差距**：无标准指标暴露，无法接入 Prometheus/Grafana 监控体系；现有 MetricsCollector 未被任何组件调用
- **建议方案**：添加 `micrometer-registry-prometheus` 依赖，通过自定义 Netty HTTP 端点暴露 `/metrics`（Prometheus 格式）；将现有计数逻辑迁移为 Micrometer Counter/Gauge/Timer；废弃手写 MetricsCollector
- **优先级**：P1
- **涉及模块**：gate-service、game-service

### 2.3 分布式链路追踪

- **当前状态**：gate-service 有 `TraceIdGenerator`（UUID 生成），但仅本地使用，未在 gRPC/Redis 调用间传播
- **差距**：跨服务请求无法关联，排查问题需手动对比多服务日志时间戳
- **建议方案**：引入 OpenTelemetry Java SDK + Zipkin/Jaeger Exporter；gRPC 通过 Interceptor 传播 TraceId；日志 pattern 中自动包含 traceId/spanId
- **优先级**：P1
- **涉及模块**：gate-service、game-service、login-service

### 2.4 结构化日志

- **当前状态**：使用 SLF4J + 默认 logback；日志为纯文本格式，包含 emoji 符号
- **差距**：纯文本日志不便于 ELK/Loki 等日志系统解析和检索
- **建议方案**：添加 `logback-spring.xml`，prod profile 使用 JSON 格式输出（logstash-logback-encoder）；dev profile 保留可读文本格式；移除 emoji 改为结构化字段
- **优先级**：P1
- **涉及模块**：全部

### 2.5 告警规则

- **当前状态**：无任何告警机制
- **差距**：连接数暴增、错误率飙升、Redis 不可达等场景无法及时发现
- **建议方案**：定义 Prometheus alerting rules（连接数阈值、gRPC 错误率、心跳失败率、Redis 延迟）；配合 Alertmanager 或 Grafana Alerting 通知
- **优先级**：P2
- **涉及模块**：运维配置

## 三、安全

### 3.1 TLS/SSL

- **当前状态**：WebSocket 使用 `ws://`（明文），gRPC 使用 `usePlaintext()`，所有通信未加密
- **差距**：消息在网络上明文传输，不满足生产安全要求
- **建议方案**：WebSocket 升级为 `wss://`（Netty SslContext）；gRPC 启用 TLS（SslContextBuilder + 证书）；通过配置开关控制（dev 可关闭）
- **优先级**：P0
- **涉及模块**：gate-service、game-service

### 3.2 Token 认证升级

- **当前状态**：`TokenService` 使用内存 ConcurrentHashMap 存储 token → playerId 映射（SecureRandom 生成 Base64 token），无 JWT，多实例不共享
- **差距**：Gate 多实例部署时 token 不互通；token 无标准签名验证；服务重启 token 全部失效
- **建议方案**：升级为 JWT（签名密钥 + 过期时间）+ Redis 黑名单（用于主动吊销）；或保留简单 token 但改为 Redis 存储实现多实例共享
- **优先级**：P0
- **涉及模块**：gate-service、login-service

### 3.3 TokenValidator 集成到消息入口

- **当前状态**：`TokenValidator` 类已存在，但 `GateNettyWebSocketHandler` 中认证仅检查 `player_id` 字段（明文 playerId，无 token 验证）
- **差距**：任何人可伪造 playerId 连接网关
- **建议方案**：在 WebSocket 认证流程中要求携带 token，调用 `TokenValidator.validate()` 验证；未认证连接仅允许发送认证消息
- **优先级**：P0
- **涉及模块**：gate-service

### 3.4 MessageEncryptor 集成

- **当前状态**：`MessageEncryptor` 使用 AES/ECB/PKCS5Padding 实现，类已存在但未被任何组件调用
- **差距**：消息体加密能力已编码但未生效
- **建议方案**：在编解码 Pipeline（GameMessageEncoder/Decoder）中根据 flags 的加密标志位调用 MessageEncryptor；将 ECB 升级为 GCM 模式（更安全）
- **优先级**：P1
- **涉及模块**：gate-service、player-client

### 3.5 REST API 鉴权

- **当前状态**：login-service 的 `/api/v1/login`、`/gate/heartbeat`、`/gate/list` 和 center-service 的 `/api/v1/config` 均无任何认证/鉴权
- **差距**：接口裸露，任何人可调用；Gate 心跳接口可被伪造
- **建议方案**：内部服务间通信使用 API Key 或 mTLS；对外接口（login）使用签名验证或 OAuth；center-service 配置接口限制为内网访问
- **优先级**：P1
- **涉及模块**：login-service、center-service

### 3.6 消息体输入校验

- **当前状态**：消息体解析后直接处理，无长度限制、类型校验或恶意内容检测
- **差距**：可能被超大消息攻击（OOM）、格式异常导致 NPE
- **建议方案**：在编解码层增加消息体最大长度限制；在 Handler 层对业务字段做 validation（使用 Jakarta Bean Validation 或自定义校验逻辑）
- **优先级**：P1
- **涉及模块**：gate-service、game-service

### 3.7 密钥管理与轮换

- **当前状态**：AES 密钥在代码中硬编码或由配置直接传入，无轮换机制
- **差距**：密钥泄露后无法自动更换
- **建议方案**：密钥存储在外部（Vault、KMS 或加密配置）；支持密钥版本号，新旧密钥并行解密期
- **优先级**：P2
- **涉及模块**：gate-service

## 四、韧性与高可用

### 4.1 RateLimiter 集成

- **当前状态**：`RateLimiter`（滑动窗口）已实现，但未被任何 Handler 或 Pipeline 调用
- **差距**：无法防止单玩家或全局消息洪水攻击
- **建议方案**：在 `GateNettyWebSocketHandler`（及未来 TCP Handler）的消息处理入口，按 playerId 和全局两级限流；触发限流时返回错误码并记录日志
- **优先级**：P0
- **涉及模块**：gate-service

### 4.2 CircuitBreaker 集成

- **当前状态**：`CircuitBreaker`（CLOSED/OPEN/HALF_OPEN 状态机）已实现，未被调用
- **差距**：当 Game 服务宕机时，Gate 持续发送 gRPC 请求，造成线程阻塞和级联故障
- **建议方案**：在 `GameGrpcClientPool.sendGameMessage` / `sendGameMessageViaStream` 中包裹 CircuitBreaker；OPEN 状态直接返回失败 + 降级响应
- **优先级**：P0
- **涉及模块**：gate-service

### 4.3 优雅关闭（Graceful Shutdown）

- **当前状态**：各组件有销毁回调（NettyWebSocketServer、GameGrpcClientPool、GameGrpcServer 等），但无统一编排；无 connection draining（停止接入新连接 → 等待存量处理 → 关闭）
- **差距**：关闭时可能中断正在处理的请求，导致消息丢失
- **建议方案**：通过 JVM shutdown hook 统一编排关闭顺序，设置 30s 超时；Netty Server 先停止 accept → flush + close existing → 关闭 EventLoopGroup；gRPC pool 等待 in-flight 完成
- **优先级**：P1
- **涉及模块**：gate-service、game-service

### 4.4 gRPC 重连改用 ScheduledExecutor + 指数退避

- **当前状态**：`GameGrpcClientPool.scheduleReconnect` 使用 `new Thread(() -> Thread.sleep(delay))`，固定延迟，无退避、无最大重试次数
- **差距**：大量 Game 同时断开时产生等量裸线程；固定延迟可能导致重连风暴
- **建议方案**：使用 `ScheduledExecutorService` 替代裸线程；实现指数退避（初始 delay → 2x → 4x → ... → maxDelay）；设置最大重试次数，超出后标记连接为 DEAD 并告警
- **优先级**：P1
- **涉及模块**：gate-service

### 4.5 连接数上限

- **当前状态**：`PlayerService` 和 `ConnectionManager` 对在线玩家数无上限控制
- **差距**：突发大量连接可能耗尽内存和文件描述符
- **建议方案**：在 `GateNettyWebSocketHandler` 的 channelActive 中检查当前连接数，超出配置上限时拒绝新连接并返回 "服务器已满" 错误
- **优先级**：P1
- **涉及模块**：gate-service

### 4.6 Redis 高可用

- **当前状态**：Redis 为单节点（docker-compose 中一个 redis:7-alpine）
- **差距**：Redis 宕机导致服务发现、离线消息、Game 状态全部不可用
- **建议方案**：生产环境使用 Redis Sentinel 或 Redis Cluster；Lettuce 客户端原生支持 Sentinel；`RedisConfig` 增加 Sentinel 配置项
- **优先级**：P1
- **涉及模块**：gate-service、game-service、login-service

### 4.7 背压（Backpressure）机制

- **当前状态**：消息处理为同步阻塞或直接写入 Stream；无流控
- **差距**：下游处理慢时上游持续写入可能导致内存溢出
- **建议方案**：gRPC Stream 侧使用 `onReady` 回调控制发送速率；Redis Stream 侧监控 pending 消息数，超出阈值暂停生产
- **优先级**：P2
- **涉及模块**：gate-service、game-service

## 五、测试

### 5.1 单元测试覆盖

- **当前状态**：gate-service 有 2 个测试文件（GameGrpcClientPoolTest、GameDiscoveryServiceTest）；game-service、login-service、center-service 均 0 测试
- **差距**：当前覆盖率约 5%，远低于生产标准（建议 >60%）
- **建议方案**：优先为核心路径补充测试：`PlayerService`、`ConnectionManager`、`GateNettyWebSocketHandler`、`MessageDispatcher`、`RateLimiter`、`CircuitBreaker`、`TokenService`；game-service 补充 `GameMessageHandler`、`GameStatusService` 测试；login/center 补充 Controller 测试
- **优先级**：P0
- **涉及模块**：全部

### 5.2 集成测试

- **当前状态**：无任何集成测试
- **差距**：无法验证 WebSocket → Gate → gRPC → Game 全链路；离线消息阈值(>200 条 relogin)、服务发现注册/注销等场景未覆盖
- **建议方案**：使用 Testcontainers（Redis）+ Netty EmbeddedChannel 编写集成测试；覆盖：WebSocket 连接认证流程、消息转发到 Game、离线消息推送、服务发现注册/注销
- **优先级**：P1

### 5.3 性能/压力测试

- **当前状态**：无性能测试
- **差距**：不清楚单 Gate 可承载的最大连接数和消息 QPS
- **建议方案**：使用 JMH 做微基准测试（编解码性能）；使用 Gatling 或自定义 player-client 多实例做端到端压测；输出性能基线报告
- **优先级**：P2
- **涉及模块**：gate-service、player-client

### 5.4 JaCoCo 覆盖率报告

- **当前状态**：Maven 未配置 JaCoCo 插件
- **差距**：无法量化测试覆盖率，CI 中无覆盖率门禁
- **建议方案**：父 pom.xml 添加 `jacoco-maven-plugin`；CI 中 `mvn verify` 后生成报告；设置最低覆盖率阈值（初期 30%，逐步提升）
- **优先级**：P1
- **涉及模块**：全部（pom.xml）

## 六、代码质量与架构

### 6.1 提取 common 共享模块

- **当前状态**：Proto 生成代码在 gate-service 和 game-service 中各自编译；`ApiResponse` 在 login-service 和 center-service 中重复定义；无共享 DTO/工具模块
- **差距**：代码重复，Proto 变更需多处同步
- **建议方案**：新建 `common` Maven 模块，包含：Proto 生成类、共享 DTO（ApiResponse 等）、工具类；其余模块依赖 common
- **优先级**：P1
- **涉及模块**：全部

### 6.2 TCP Server 启动集成

- **当前状态**：`NettyTcpServer`、`TcpMessageHandler`、`TcpChannelInitializer`、`TcpHeartbeatHandler` 类均已存在，但 `NettyTcpServer` 非 Spring 组件，未在启动流程中被调用
- **差距**：TCP 端口（8889）从未开启，TCP 能力不可用
- **建议方案**：将 `NettyTcpServer` 注册到 DI 容器（或在启动入口手动初始化），通过配置开关 `gate.tcp.enabled` 控制是否启动；复用 `MessageDispatcher` 处理 TCP 消息
- **优先级**：P1
- **涉及模块**：gate-service

### 6.3 GateClusterManager 集成

- **当前状态**：`GateClusterManager` 已实现实例注册、心跳、不健康实例剔除逻辑，但未被任何组件注入或调用
- **差距**：多 Gate 实例间无感知，无法实现跨实例消息路由或负载信息共享
- **建议方案**：在 GateServiceApplication 启动后注册本实例到 Redis（类似 GameRegistryService 的模式）；login-service 的 GateService 已有 Gate 心跳接收逻辑，需对接
- **优先级**：P1
- **涉及模块**：gate-service、login-service

### 6.4 GameMessageHandler 业务逻辑补全

- **当前状态**：`GameMessageHandler.handleGameMessage` 中 `battle.move` 和 `chat.message` 处理为 stub（仅打印日志，标注 TODO）
- **差距**：Game 服务无实际业务逻辑，仅为框架空壳
- **建议方案**：根据业务需求实现具体消息处理逻辑；至少实现一个完整 echo 或 broadcast 示例，证明全链路可用
- **优先级**：P1
- **涉及模块**：game-service

### 6.5 统一异常处理

- **当前状态**：gate-service 中异常处理为零散 try/catch + log；REST 服务无全局异常处理
- **差距**：异常信息格式不统一；某些异常可能导致连接泄漏
- **建议方案**：gate-service 在 Netty Handler 中增加统一 `exceptionCaught` 处理（记录 + 关闭连接 + 发送错误响应）；login/center 添加 HTTP Filter/Interceptor 实现全局异常处理，返回统一错误格式
- **优先级**：P1
- **涉及模块**：全部

### 6.6 API 版本管理

- **当前状态**：login-service 使用 `/api/v1`，center-service 使用 `/api/v1`；无版本迁移策略
- **差距**：后续接口变更时无法平滑过渡
- **建议方案**：文档化版本策略（URL 版本 vs Header 版本）；建立接口废弃流程（deprecated → removed）
- **优先级**：P2
- **涉及模块**：login-service、center-service

## 七、配置与服务治理

### 7.1 外部配置中心

- **当前状态**：各服务使用本地 `application.yml` + 环境变量覆盖；`center-service` 仅下发客户端配置（版本号、SDK 地址），不为其他服务提供配置
- **差距**：配置变更需重新部署；无法动态调整限流阈值、心跳间隔等运行时参数
- **建议方案**：方案一：使用 Nacos 作为配置中心（与服务发现统一）；方案二：升级 center-service 为内部配置源 + Nacos SDK；方案三：用 K8s ConfigMap + 热更新
- **优先级**：P2
- **涉及模块**：全部

### 7.2 配置热更新

- **当前状态**：所有配置仅在启动时加载，运行时不可变
- **差距**：调整限流阈值、日志级别、心跳间隔等需重启服务
- **建议方案**：使用 Nacos SDK 监听配置变更回调，或自定义配置热加载机制（定时拉取 + 回调通知）
- **优先级**：P2
- **涉及模块**：gate-service、game-service

### 7.3 敏感信息外置

- **当前状态**：Redis 密码在 `application.yml` 中明文配置（`password: redistest`）
- **差距**：密码泄露风险；不符合安全审计要求
- **建议方案**：生产环境通过环境变量或 Secret Manager（K8s Secret、Vault）注入；`application.yml` 仅保留 `${REDIS_PASSWORD}` 占位
- **优先级**：P1
- **涉及模块**：全部

### 7.4 统一服务注册与发现

- **当前状态**：Game 服务使用 Redis 手工注册（`GameRegistryService`）；Gate → Login、Gate → Center 的地址在配置中硬编码
- **差距**：服务间寻址方式不统一；新增实例需修改配置重启
- **建议方案**：统一使用 Nacos 或 Consul 做服务注册发现；所有服务启动时注册，调用时通过服务名解析；现有 Redis 注册逻辑可保留作为游戏领域专用（Game 状态），但通用服务发现独立
- **优先级**：P2
- **涉及模块**：全部

## 八、API 文档

### 8.1 REST API 文档（OpenAPI/Swagger）

- **当前状态**：login-service 有 4 个 REST 端点（`/api/v1/login`、`/game/login-record`、`/gate/heartbeat`、`/gate/list`），center-service 有 1 个（`/api/v1/config`），均无 API 文档
- **差距**：调用方需阅读源码了解请求/响应格式
- **建议方案**：使用 Swagger Core 注解标注 REST 接口，通过 Maven 插件生成 OpenAPI 3.0 文档；可独立部署 Swagger UI 或生成静态 HTML 文档
- **优先级**：P1
- **涉及模块**：login-service、center-service

### 8.2 gRPC Proto 文档化

- **当前状态**：`proto/game_service.proto` 定义了 3 个 RPC（SendGameMessage、StreamCommunication、Heartbeat），无详细注释或独立文档
- **差距**：gRPC 接口的语义、错误码、使用约定不清晰
- **建议方案**：在 proto 文件中添加详细注释（每个 message、field、service、rpc）；使用 protoc-gen-doc 生成 HTML/Markdown 文档
- **优先级**：P2
- **涉及模块**：proto/

### 8.3 接口变更管理

- **当前状态**：无接口变更记录或兼容性检查
- **差距**：Proto 或 REST 接口变更可能破坏已有客户端
- **建议方案**：Proto 使用 `buf` 做 breaking change 检测；REST 接口变更记录在 CHANGELOG 中
- **优先级**：P2
- **涉及模块**：全部

## 九、数据与存储

### 9.1 持久化存储方案

- **当前状态**：项目仅使用 Redis（服务发现、离线消息、Game 状态、Gate 心跳、Token 存储），无关系型或文档数据库
- **差距**：玩家数据、游戏记录、日志审计等持久化需求无法满足；Redis 重启数据全部丢失（除非开启 RDB/AOF）
- **建议方案**：根据业务需求引入 MySQL/PostgreSQL（玩家账号、游戏记录）或 MongoDB（日志、事件）；Redis 仅用于缓存和实时数据
- **优先级**：P1
- **涉及模块**：game-service、login-service

### 9.2 Redis 数据 TTL 与容量规划

- **当前状态**：部分 Redis key 有 TTL（如 Game 注册信息），但离线消息、Gate 心跳等数据无明确 TTL 或清理策略
- **差距**：长期运行后 Redis 内存持续增长，可能导致 OOM
- **建议方案**：为所有 Redis key 规划 TTL（离线消息 7 天、心跳 2 分钟、Token 与 session 过期同步）；配置 Redis maxmemory + eviction policy
- **优先级**：P1
- **涉及模块**：gate-service、game-service、login-service

### 9.3 数据备份与恢复

- **当前状态**：Redis 单节点，无备份策略
- **差距**：数据丢失后无法恢复
- **建议方案**：开启 Redis RDB 定期快照 + AOF 持久化；生产使用 Redis Sentinel/Cluster 实现数据冗余；如引入数据库则配置定期备份
- **优先级**：P2
- **涉及模块**：运维配置
