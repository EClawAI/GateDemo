6. **接入 ConnectionManager，统一连接生命周期管理**
   - **现状**：`ConnectionManager`（含 `PlayerConnection` 状态机、连接数上限、定时心跳踢线）已为 `@Service`，但全项目无任何注入与调用；实际在线表与注册/注销在 `PlayerService`（`ConcurrentMap<Long, Channel>`），认证成功时在 `GateNettyWebSocketHandler` 中调用 `registerPlayer` / `unregisterPlayer`。
   - **目标**：由 ConnectionManager 承载「连接注册、认证状态、心跳超时、连接数 cap」；`PlayerService` 聚焦发消息、离线消息等玩家侧业务，或内部委托 ConnectionManager 查询 Channel，避免两套 Map 长期并存。
   - **落地要点（便于逐项改）**：
     - 在认证成功路径调用 `registerConnection` + `authenticate`（或先注册再区分未认证状态，与现网顶号逻辑对齐）；断开 / 顶号关闭旧连接时调用 `unregisterConnection`。
     - 心跳消息路径调用 `renewHeartbeat`，与 `ConnectionManager` 定时任务联动；评估 WebSocket 与 TCP（若共用）Handler 是否都要接线。
     - 将依赖 `PlayerService::getOnlineCount` / `getPlayerChannel` / `hasPlayer` 的模块（如指标、优雅下线、gRPC 流）改为以 ConnectionManager 为数据源，或保留 PlayerService 薄封装对外 API 不变。
     - 明确与 `ConnectionLimiter` 的职责边界（接受连接时限流 vs 认证后 player 表上限），避免双重限制冲突或遗漏。
7. **未认证占连接防护**：未认证连接在 `MessageValidator` 失败时只 `sendError` 不断连，且入站读会刷新读空闲，攻击者可持续占满 `ConnectionLimiter`/`gate.max-connections` 槽位形成连接耗尽型 DoS/DDoS。需补强：未认证会话最长存活（建连/首包起计时）、校验失败累计或恶意模式主动断连+限连、按 IP/网段的建连速率与并发连接上限、与全局限流/ConnectionManager 生命周期策略对齐。
8. **补全 OfflineMessageService / Redis Stream 离线消息闭环**
   - **现状**：`PlayerService.unregisterPlayer` 会调 `OfflineMessageService.onPlayerOffline`，但实现仅打日志；`onPlayerOnline`（查 `MessageQueueProducer.getOfflineMessageCount`、超阈值 `RELOGIN_REQUIRED`、否则 `handleNormalMode` 推送）**全项目无调用**；`MessageQueueProducer.saveOfflineMessage` **无引用**，离线堆积不会被写入。
   - **目标**：下线侧按需更新状态或触发入队策略；玩家认证成功并入 `PlayerService` 后调用 `onPlayerOnline`，实现 `handleNormalMode` 从 Stream 消费并 `sendToPlayer`；game→gate 在玩家不在线时写入离线队列，并与 docs 已有「断线缓存」项对齐。
   - **落地要点**：在 `GateNettyWebSocketHandler`（或统一注册点）认证成功后调用 `onPlayerOnline(playerId, channel)`；明确 `ErrorResponse` 与客户端重登协议；为 `saveOfflineMessage` 增加调用方（如 gRPC 下行或 Dispatcher）；补充集成测试覆盖阈值分支与空 Stream。
9. **补全 TCP 接入与 WebSocket 对等能力**
   - **现状**（`gate.tcp.enabled=true`）：`TcpMessageHandler` 仅将 `WrappedMessage` 交给 `MessageDispatcher`，默认只注册 `AuthRequest` / `ClientHeartbeat` 占位处理器；其余 `messageId` 直接 `No handler`，**不会**走 `MessageRouteRegistry` → `ServiceRouterManager` → `GameServiceRouter` → `GameGrpcClientPool`，**客户端经 TCP 发往 game 的业务消息当前无法 RPC 到 game-server**。TCP 侧亦无 `GateNettyWebSocketHandler` 同款 token 校验、`PlayerService` 注册、`gameId` Channel 属性、限流与熔断、`ConnectionLimiter` 等。
   - **目标**：TCP 与 WS 共享同一套路由与转发语义（认证协议、顶号、按 `messageId` 转发 game/center 等），下行推送亦能写回同一 `Channel`；或明确文档声明 TCP 仅为调试/局部场景并限制路由表。
   - **落地要点**：抽取可复用的「鉴权 + 路由 + 转发」逻辑供 WS/TCP 共用，或在 TCP pipeline 尾部挂与 WS 一致的业务 Handler；为 TCP 补齐连接数与限流策略；game 下行若经 gRPC 回调需能定位 TCP `Channel`；补充 TCP 集成测试覆盖转发与多服务路由。
10. **抽取 WS/TCP 共用帧解析，消除 GameMessageDecoder 与 WebSocketBinaryDecoder 重复**
   - **现状**：二者均实现同一套 16 字节头 + body + 可选 DEFLATE 解压，并产出 `WrappedMessage`；TCP 侧为 `ByteToMessageDecoder`（粘包/半包 `mark`/`reset`），WebSocket 侧为 `MessageToMessageDecoder<BinaryWebSocketFrame>`（整帧即一条消息）。逻辑复制，修 bug/改上限需改两处；注释里仍存在「14 字节头」等笔误。
   - **目标**：单一真相来源（如 `GameFrameCodec`/`parseFrame(ByteBuf, FrameSource)`）：负责 `bodyLength` 校验、读 body、解压、组 `WrappedMessage`；`GameMessageDecoder` 只负责从流式 `ByteBuf` 判定可读长度并调用解析；`WebSocketBinaryDecoder` 只负责从 `frame.content()` 调用解析（不完整则关连）。
   - **落地要点**：统一常量 `HEADER_SIZE`/`MAX_BODY_LENGTH` 与解压实现；为解析层补充单元测试（压缩标志、非法长度、边界长度）；回归 TCP 半包与 WS 整帧两条 pipeline。
