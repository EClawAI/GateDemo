# 游戏网关服务开发方案

## 一、项目概述

### 1.1 当前项目状态

本项目是一个游戏网关服务的Demo，采用微服务架构：

```
┌─────────────────┐     WebSocket      ┌─────────────────┐     gRPC      ┌─────────────────┐
│  Player Client  │ ──────────────────►│   Gate Service  │──────────────►│  Game Service   │
│   (玩家客户端)    │                    │   (网关服务)     │               │   (游戏服务)     │
└─────────────────┘                    └─────────────────┘               └─────────────────┘
```

**现有组件**：
- **Gate-service**: WebSocket网关，基于Netty实现
- **Game-service**: 游戏逻辑服务，gRPC通信
- **Player-client**: 测试客户端

**现有功能**：
- WebSocket连接管理
- 基础认证（player_id）
- 心跳检测（IdleStateHandler）
- 消息转发到Game服务
- gRPC客户端连接池

### 1.2 消息结构定义

根据你提供的要求，消息结构如下：

```java
/**
 * <ul>
 * <li>总共分为6部分</li>
 * <li>第1部分，标志位，占2字节
 * <ul>
 * <li>第15位，是否压缩</li>
 * <li>第7位和第6位，请求响应模式</li>
 * <li>其他暂时保留</li>
 * </ul>
 * </li>
 * <li>第2部分，sequence，占用2字节，无符号，范围0 - 65535，<strong>这部分为可选，现在只用于客户端</strong></li>
 * <li>第3部分，消息类型，占用2字节，无符号，范围0 - 65535</li>
 * <li>第4部分，消息体长度，占用4字节，范围0 - 2147483647</li>
 * <li>第5部分，请求id，占用4字节，范围0 - 2147483647，<strong>这部分为可选</strong></li>
 * <li>第6部分，消息体，具体格式可以自定义</li>
 * </ul>
 */
```

## 二、当前网关缺少的功能分析

| 功能 | 当前状态 | 缺失影响 |
|------|----------|----------|
| 断线重连 | 无 | 弱网环境下用户体验差 |
| 自动重连机制 | 无 | 需手动重连 |
| 连接状态追踪 | 无 | 无法感知连接状态变化 |
| 离线消息缓存 | 无 | 断线期间消息丢失 |

| 功能 | 当前状态 | 缺失影响 |
|------|----------|----------|

### 2.4 安全与限流（中优先级）

| 功能 | 当前状态 | 缺失影响 |
|------|----------|----------|

### 2.5 监控与运维（低优先级）

| 功能 | 当前状态 | 缺失影响 |
|------|----------|----------|

## 三、开发方案

### 3.1 方案设计原则

1. **二进制协议优先**：使用二进制消息替代JSON，减少带宽
2. **模块化设计**：各功能独立模块，便于维护和扩展
3. **可配置化**：路由规则、限流策略等可配置
4. **平滑升级**：支持与现有JSON协议共存，逐步迁移

### 3.2 消息结构设计

```
┌─────────────────────────────────────────────────────────────────────┐
│                        消息结构（字节流）                             │
├──────────┬──────────┬──────────┬────────────┬────────────┬──────────┤
│  标志位   │ Sequence │  消息ID   │   消息长度  │   请求ID   │  消息体   │
│  2字节   │  2字节    │  2字节    │   4字节     │   4字节    │  N字节    │
├──────────┴──────────┴──────────┴────────────┴────────────┴──────────┤
│  0        1        2        3        4        5        6        N    │
└─────────────────────────────────────────────────────────────────────┘
```

**标志位定义**：
- 第15位（0x8000）：是否压缩
- 第14位（0x4000）：是否加密
- 第7-6位（0x00C0）：消息模式
  - 00：请求（Request）
  - 01：响应（Response）
  - 10：通知（Push/Notification）
  - 11：保留

### 3.3 消息ID生成策略

使用消息名hash生成消息ID：
1. 消息名格式：`{模块}.{功能}`，如 `battle.move`, `chat.send`
2. 使用 FNV-1a 或 MurmurHash 算法计算hash
3. 取hash的低16位作为消息ID
4. 手动维护消息名到ID的映射表

#### 计划2.3：离线消息缓存（复用 Redis Stream）

**任务内容**：
- 复用 Redis Stream 存储离线消息（与消息队列共用资源）
- 玩家上线后检查离线消息数量
- **智能推送策略**：
  - 离线消息 ≤ 阈值（默认200条）：逐条推送
  - 离线消息 > 阈值：丢弃队列 + 通知Game发送relogin

**设计思路**：
- 消息队列和离线消息缓存使用同一个 Redis Stream
- 实时消息：在线消费者的消费者组处理
- 离线消息：玩家上线后从对应消费者组拉取

**推送策略**：
| 离线消息数量 | 推送方式 | 说明 |
|-------------|---------|------|
| 0-200条 | 逐条推送 | 正常消息，逐条发送到客户端 |
| >200条 | Relogin流程 | 丢弃队列 → 通知Game发送relogin → Game重新登录下发全量数据 |

**消息流程**：
```
Gate检测离线消息 > 200条时：
  1. 丢弃Stream中的离线消息（XACK + XDEL）
  2. 向Game发送 relogin 消息（消息ID: auth.relogin）
  3. Game收到relogin → 执行玩家重新登录逻辑
  4. Game下发全量数据（玩家数据、排行榜、背包、奖励等）
```

**交付物**：
- `gate/service/OfflineMessageService.java`
- `gate/config/OfflineMessageConfig.java`
- `proto/auth.relogin` 消息定义

**依赖**：
- 计划2.2

## 五、技术选型建议

### 5.1 消息队列选型

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| Redis Stream | 简单、轻量、与现有架构兼容 | 功能有限 | 小规模项目 |
| RabbitMQ | 功能丰富、可靠性高 | 性能一般 | 中等项目 |
| Kafka | 高吞吐、可持久化 | 延迟较高 | 大规模项目 |

**推荐**：先使用 Redis Stream，后期可迁移到 Kafka

### 5.2 限流选型

- 分布式限流：Redis + Lua脚本
- 本地限流：Bucket4j

### 5.3 监控选型

- Micrometer + Prometheus
- 自定义Metrics接口

### 8.3 TCP vs WebSocket对比

| 特性 | WebSocket | TCP |
|------|-----------|-----|
| 协议 | HTTP升级 | 原生TCP |
| 头开销 | 约60字节（握手） | 无 |
| 适用场景 | 浏览器/Web | App/游戏客户端 |
| 心跳 | WebSocket Ping/Pong | 自定义心跳 |
| 断线检测 | 依赖IdleStateHandler | 自定义心跳 |

## 十一、总结

本方案涵盖了游戏网关服务的完整开发路线，从基础的消息协议到分布式部署，逐步完善网关的各项功能。建议按照计划的优先级有序开发：

1. **优先级高**：消息协议、断线重连（直接影响用户体验）
2. **优先级中**：消息路由、限流（系统稳定性）
3. **优先级低**：监控、分布式（运维能力）
